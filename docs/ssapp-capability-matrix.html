Documentation / SSApp capability matrix

SSApp remote capability matrix

Read in Markdown

Use this matrix to implement and validate complete remote workflows in Social Stream Ninja Standalone (SSApp). Start with the remote setup guide, then select the workflow and row IDs that apply. Each row defines the intended behavior, current integration route, remaining work, and an observable acceptance check. The scope is SSApp and its owned surfaces; external desktop applications, model execution, and repository publishing have separate owners.

Reading and maintaining the matrix

The implementation baseline is SSApp 0.4.38, control API 1.4.1, local MCP adapter 1.3.1, and Ninja MCP 0.4.2 with the SSApp backend. Runtime discovery is authoritative. A package version alone does not establish that a particular source mode, permission, or workflow is available.

Settings-export support requires the updated 0.4.38 development build advertising API 1.5.0 / MCP 1.4.0 and the Ninja MCP settings-export helper. See the backup workflow. The existing 0.4.38 release does not imply these additional commands are available.

State Meaning and action
Implemented A supported code path exists through the remote bridge. Run the stated acceptance check for the intended environment.
Partial Some required behavior exists; the row identifies the remaining part.
UI path The application has a relevant UI and generic controls can reach it, but no dedicated complete command contract exists. Exercise the whole workflow before relying on it.
Missing No SSApp integration route provides the described capability. Implement it before advertising support.
External A cooperating application, model harness, human, or development tool owns this part. Document and validate the handoff.

Implementation and validation are separate dimensions. Record verification as Not run, Supporting check, Local app verified, Remote app verified, Inconclusive, or Failed, using the evidence record. Do not infer a passed remote workflow from forwarding its schema. Preserve stable row IDs when adding or splitting requirements.

Priorities describe delivery order: P0 = dependable remote control; P1 = broad app workflows and operational completeness; P2 = optional live media, advanced sharing, and development extensions. An implemented P0 row still needs regression validation. Optional P2 features need not block a clearly scoped claim of complete screenshot-based app control.

References such as N1 and S3 resolve in the implementation reference map. N = Ninja MCP, S = SSApp, C = Social Stream, E = external adapter. V01–V12 are reusable validation procedures below; each row adds its particular expected result. Owner names indicate where to make a change, not permission to change unrelated behavior.

Validation procedures

Use an isolated SSApp profile, controlled fixture pages and independently observed host state. On Windows run natively, not through WSL. Use actual SSApp for app behavior; unrelated Chrome is suitable only for the HTML documentation itself. Never use the CamCam66Gaming channel. Do not restart or reconfigure shared relay/mailbox services as an incidental test step. Keep fixtures, credentials, logs and screenshots outside public checkouts. Cap concurrent worker pools to at most half the host's logical processors, using a lower limit if the machine becomes sluggish.

Each procedure requires an explicit result: passed within the recorded scope, failed, or inconclusive. No fresh runtime run is implied by a matrix row's implementation state.

V01 — Connection and contract

Use the setup guide with an isolated app and private worker/client credentials. Run node scripts/vdo-mcp-ssapp.js --doctor --config <private-agent-config> from the Ninja MCP checkout. Capture initialize, tools/list, status and capabilities through the actual remote client. Record versions, instance ID, role, tool names and route; omit credentials. Compare permitted schemas and image/error shapes with the host adapter. Repeat while the app is offline, loading, then ready; try an unsupported command and a wrong credential. Verify that enabling headless mode alone does not enable the API. For multi-instance claims, use separate ports and independent fixture markers. A doctor success alone does not satisfy a browser, capture or source workflow.

V02 — Browser surface and input

Serve a controlled page containing labelled fields, a click counter, nested scroll panels, same-origin and cross-origin frames, a canvas, drag/drop zones, touch event markers, delayed controls and popup buttons. Create it through the real SSApp window path. Establish positions/state independently on the host fixture. Drive all tested actions from the remote MCP connection. Check exact text, event type, button/contact count, drag payload, focus, window bounds and side effects. Repeat selected cases hidden, minimized, zoomed and resized. Test stale IDs after navigation/close and references after expiry. Record screenshot hash/dimensions and map coordinates using screenshotId; a successful input response without the expected fixture effect is not a pass. Validation code may observe fixture state; production tools must not depend on arbitrary page-script injection by the agent.

V03 — Authentication, dialogs and human handoff

Start with fixture sign-in fields and JavaScript/Electron prompts, then use an authorized test account for each real platform whose support will be claimed. Open the correct session's sign-in flow, observe the resulting popup and validate account isolation. Exercise accept/cancel/default/checkbox/file choices. Trigger a blocking prompt while another request waits; answer it through the recovery tools. For human steps, release or suspend control, show the correct host surface, let the person complete the step, then re-discover and resume once. Record only non-secret evidence of the resulting account/source state. Fixture password entry does not establish real OAuth, passkey or CAPTCHA completion.

V04 — Files and artifacts

Use temporary task-owned directories with known small, multiple, Unicode-named and boundary-size files. Test denied and permitted host-file clients; establish hashes before transfer. Check browser selection and actual upload receipt separately. Exercise missing files, cancellation, transfer interruption, partial downloads, quota exhaustion and expiry. Verify exported/retrieved artifact hashes and reject path substitution outside the grant. Cleanup must preserve unrelated host files. Until staging/download tools exist, mark those subcases missing rather than treating a generic file transfer as full SSApp support.

For settings export, compare its decoded payload with an ordinary File-menu export, allowing only the export timestamp to differ. Include a multi-chunk backup, denied permissions, observer and other-client reads, missing confirmation, path substitution, a dropped reply, expiry, restart, size limits, checksum corruption and release during transfer. Verify the agent destination is created only after integrity checks and an existing file is never replaced. Exercise normal export success/cancel while automation is enabled and after an automation export; its dialogs, filename, contents and destination must match ordinary behavior, and normal exports must not become automation artifacts. Retrieve multiple near-limit backups within the retry-retention window; later calls must still complete. Drop a chunk reply and retry the immutable read, checking its hash and retained request fingerprint. Export/release mutations must continue to return their original cached receipts.

V05 — Transport and lifecycle faults

Use two computers for remote claims, logging actual route and host-side effects. Exercise WebRTC, HTTP-only and automatic fallback separately. Drop a response after a non-idempotent fixture action has executed, then retry with the same request identity over the alternate route. Require one host effect and the original result. Test request-ID conflicts, duplicate chunks, slow receivers, oversized envelopes, expired requests, cache expiry and 4 MB image payloads. Restart app, adapter and worker separately; do not assume exactly-once execution across lost process-local caches. Check uncertain-outcome handling, reconciliation, stale-instance rejection and fresh discovery. Verify queue revocation, active-action limitations, bridge shutdown and app persistence. Record route/ID/result/effect together; encrypted send acceptance alone is not completion. Use local fault injection rather than disrupting shared infrastructure.

V06 — Permissions and ownership

Create controller A, controller B, observer and restricted-tool credentials. Test normal and direct calls to hidden tools, forged identity, absent/expired lease, renewal, revocation, reconnect and queued work. Observe independently that denied calls cause no effect. Try file paths through both chooser and dialog routes. For future target grants, include default-main-window calls, parent/child popups, menus, bulk actions, dialogs, screenshots and source aliases. Plant synthetic private values and hostile instructions in fixture content; verify redaction plus the consuming harness's task boundaries. Do not claim target isolation when only a tool allowlist exists.

V07 — Sources and delivery

Choose an affected platform/mode and intended destinations. Establish independently known eligible input IDs or occurrence-aware fixture tokens, including two distinct identical-text messages. Define interval, history/filter/moderation exclusions and pending-message drain in advance. Collect input, capture and actual destination ledgers, not just totals or periodic samples. Compare every eligible identity exactly once per intended destination and report missing, duplicate and unexpected identities at each stage. Exercise relevant bursts, delayed rows, pruning, edits/moves, hidden windows, pause/resume, reload/replay, reconnect and stream changes. Check persistent source/group/settings state separately. No input evidence, disabled capture, no eligible traffic or unavailable destination output means inconclusive. Loss/duplication fixes require original-failing/final-passing controlled cases plus actual live chat in SSApp for each affected source and mode. Use S8 as a starting point, not as a substitute for the required evidence.

V08 — Media and observation lifecycle

Use a selected fixture surface with a visible monotonic clock and optional known audio tone. Observe from another computer, measure frame freshness and input latency under constrained bandwidth, and verify unselected surfaces/audio devices are absent. Test unsubscribe, revoke, target close and route loss; bridge-owned capture must stop. Preserve screenshot-based fallback and coordinate mapping. Distinguish WebRTC publishing, viewer playback and model understanding as three separate results. Record microphone, app-audio and recording choices independently; ordinary app startup must not start capture.

V09 — Diagnostics

Induce one fault at a time: invalid URL, expired test authentication, request failure, missing page element, disabled capture, known filter exclusion, unreachable destination and resource pressure. Compare the agent's diagnosis with the injected cause. Require a source/instance/version/time-scoped explanation and an appropriately scoped recovery. Bound observations and redact synthetic secrets. Repeat with no eligible traffic; the agent should report uncertainty instead of inventing a capture verdict. A useful diagnostic bundle needs evidence of both failure and recovery and must be retrievable through an authorized route.

V10 — Ordinary use, persistence and host matrix

Compare normal startup with automation disabled against the established baseline: appearance, settings, sessions, window focus, native dialogs, network listeners and idle work. Then enable automation and test hidden/headless workflows, restarts and shutdown/disconnect behavior. Compare settings and source state before/after; verify that no unrelated account or compatibility flag changed. Run on Windows, macOS and Linux before claiming all three; test representative display scale, keyboard layout and installed-package launches. Record long-run duration, reconnect count and resource trend. A Windows result does not establish macOS/Linux host behavior; a Linux agent controlling Windows is still a Windows host result.

V11 — Agent interoperability and complete tasks

Use actual named clients/model versions, not only a protocol simulator. Each should discover tools, view an image, identify a control, claim, act, verify and release. Exercise errors, large images and recovery with an unfamiliar page without custom per-page automation code. For a local model, configure the endpoint in the external harness, then measure task success and observation budget. A model recognizing an image and a transport returning image bytes are separate checks. Handoffs must retain task intent while discarding stale references and acquiring a new valid lease.

V12 — Diagnosis-to-patch

Use separately authorized development access to the correct source checkout. Record source revision/hash, affected mode, reproduction and independent expected output. Demonstrate the original failure in SSApp, apply a narrow change, rerun the same case and relevant regressions, then demonstrate rollback. Follow live-delivery requirements for capture loss/duplication. Produce a diff and evidence suitable for review. Branch creation, PR submission, push, release and deployment follow their own explicit authorization and repository rules. Do not turn ordinary chat or a received file into code execution permission.

These workflows prevent broad tool coverage from being mistaken for complete user outcomes.

Implementation sequence

  1. Preserve the existing P0 controls and recovery behavior. Complete the V01/V02/V03/V05/V06 fixture workflow across the remote bridge, including stale-instance, large-image and blocked-prompt cases.
  2. Close P0 observation gaps: useful readiness/navigation diagnosis, bounded state waits, target lifecycle notifications and authentication/human-handoff outcomes. Add direct commands only where existing UI observation cannot reliably express or verify the task.
  3. Exercise source setup, capture repair and export workflows. Address group/session UI gaps and establish independent destination evidence. Do not expand source capture behavior as an incidental bridge change.
  4. Implement staged files/download/artifact handles with scoped permissions, then selected-target grants if remote operators need narrower access than the whole app.
  5. Add remote live frames and optional audio using the SDK and explicit subscription lifecycle. Keep model integration optional. Build development/patch access and ninja-p2p handoffs as separate cooperating layers.

For every added capability, change the owning layer, preserve schema/instance/error semantics, update runtime discovery and the canonical SSApp skill, and validate the linked row plus the end-to-end workflow it enables. Keep both versions of this matrix synchronized. This sequence is a planning order; it does not authorize unrelated platform, account, infrastructure, repository or deployment changes.

Evidence record

Keep execution records outside the public repository. Use one record per row and environment, with these fields; a single successful fixture run should not silently mark all related rows passed.

Field Required detail
Matrix row and workflow Stable row ID(s), requirement exercised, exact fixture/scenario.
Implementation revision SSApp, source files, Ninja MCP and relevant SDK revision/hash; dirty-file digest if applicable.
Environment Host/agent OS, app/API/MCP/client/model versions, profile, display/keyboard conditions.
Route and scope Actual WebRTC/HTTP/fallback route, same-machine vs two-computer, permissions and granted targets.
Observation interval Start/end, drain period, duration and repeated-event/reconnect counts.
Independent oracle Expected input/state, how obtained independently, actual app/destination observation.
Outcome Not run, supporting check, local app verified, remote app verified, inconclusive or failed; reason and scope.
Artifacts Redacted logs, result JSON, screenshot hashes, expected/observed ledgers, reproduction command.
Remaining coverage Specific unsupported/untested modes, platforms and fault conditions; next required check.

Retain failures and inconclusive results alongside later passes. Generic code inspection, protocol tests, mock servers, schema checks and documentation checks are supporting evidence, not real SSApp workflow validation. A retained summary with no per-case details supports only the scope it actually records.
