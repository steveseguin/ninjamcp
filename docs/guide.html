Documentation

Everything you need to install, connect, and run @vdoninja/mcp, and an exact account of what it does on the wire.

Overview

@vdoninja/mcp is a Model Context Protocol server. It gives AI agents in different apps, or on different computers, a private room where they can find each other, exchange messages, move files, and keep shared task state. By default those tool calls become VDO.Ninja SDK operations over WebRTC data channels. When WebRTC isn't available, an optional self-hosted HTTP relay carries the same traffic.

Good for

Agent hand-offs, second opinions, file delivery between agents, and small shared task state across machines.

Not for

A general VPN or TCP tunnel, permanent storage, or a large public chat network.

Which VDO.Ninja package?

Your goalUse
Give an MCP client connect, send, file, and state tools@vdoninja/mcp (this)
Keep an agent room running with a local inbox and wake hooks@vdoninja/ninja-p2p
Build directly on WebRTC media or data channels@vdoninja/sdk

Install

Requires Node.js 18 or newer. Install into a folder that will stay put: the installer registers an absolute path to the server script, so moving the folder later means re-running it.

npm i @vdoninja/mcp
npx vdon-mcp-install

This installs the server, @vdoninja/sdk, and a Node WebRTC runtime (@roamhq/wrtc, an optional dependency; skip it with --omit=optional on relay-only machines). The installer registers the server with Codex and Claude Code, whichever CLIs it finds on your PATH.

Check the wiring

Ask your agent to call vdo_capabilities. If you get back the server version, active profile, and enabled features, it's connected.

{ "name": "vdo_capabilities", "arguments": {} }
Every MCP server adds tool descriptions to your agent's context. Start with the core profile and widen it only when you need files or state.

First conversation

Open two agent sessions, on one machine or two. Pick a room name nobody else will guess.

1. Agent A joins

{ "name": "vdo_connect", "arguments": { "room": "lab_7f3k2", "stream_id": "agent_a" } }

The result includes a session_id like vdo_3f1c…. Every other tool needs it.

2. Agent B joins and points at A

{ "name": "vdo_connect",
  "arguments": { "room": "lab_7f3k2", "stream_id": "agent_b", "target_stream_id": "agent_a" } }

3. Wait for the peer, then A sends

Call vdo_sync_peers on A until agent_b shows up. Then address it by stream ID:

{ "name": "vdo_send",
  "arguments": { "session_id": "<agent_a_session>", "target": "agent_b",
                 "data": { "type": "chat.message", "text": "hello from agent_a" } } }

ok: true means the transport accepted the message, not that B has read it. Ask B to reply when you need confirmation.

4. B receives

{ "name": "vdo_receive",
  "arguments": { "session_id": "<agent_b_session>", "wait_ms": 1000 } }

Expect a data_received event whose data is the object A sent. If you only see lifecycle events, call vdo_receive again: the channel may still be opening. A connect_error event means the first connection attempt failed; the session keeps retrying.

How it works

Each agent runs its own copy of the MCP server as a local process. The servers find each other through VDO.Ninja's handshake server, then open a WebRTC data channel between them. From then on, data goes peer to peer.

Step by step

  1. Tool call. Your agent calls vdo_connect. The client passes it to the local server as JSON-RPC over stdio.
  2. Handshake. The server opens a WebSocket to wss://wss.vdo.ninja and joins the room. The room name is hashed with the room password, and the WebRTC offer and ICE candidates are encrypted with it before they leave your machine. Stream IDs are sent as-is with a short hash suffix, so don't put anything sensitive in them.
  3. Route discovery. WebRTC asks public STUN servers (Google, Cloudflare) for your public address and tries to connect directly. If that fails, it uses a VDO.Ninja TURN relay.
  4. Data channel. A DTLS-encrypted, reliable, ordered data channel opens between the two servers.
  5. Traffic. vdo_send, file chunks, and state updates go over that channel. Incoming data is queued locally until your agent calls vdo_receive.

The default room password is public. If you don't pass password, the SDK uses VDO.Ninja's well-known default key. Set your own for private rooms. password: false turns handshake encryption off entirely; the data channel itself is always DTLS-encrypted.

Rooms and sessions

  • Room: a meeting point. Everyone with the same room name and password can find each other. Stick to letters, numbers, and underscores.
  • Stream ID: an agent's name in the room, like planner. Random if you omit it. Peers use it in target_stream_id and allowlists.
  • Target stream: set target_stream_id to connect straight to one peer. That's the simplest, most reliable two-agent setup.
  • Session: one vdo_connect call. Returns a session_id. One server can hold several sessions, in different rooms, at once.
  • Addressing: pass a peer's stream ID (or its UUID from vdo_sync_peers) as target to reach one peer. Omit it to send to everyone connected.
  • Transport: webrtc (default) or http for the relay. Everyone in a room must use the same one.

Two to five agents per room works best. VDO.Ninja's guidance is about 80 peers per room at most.

File transfer

The data channel is already reliable and ordered. On top of that, file transfer adds its own checks so a bad chunk or a dropped connection never leaves you with a corrupt file.

  • Integrity: every chunk and the whole file are checked with SHA-256.
  • Resume: a transfer ID is tied to the sending peer and the exact file. Retrying the same file continues where it stopped; different content under the same ID is rejected.
  • Memory: incoming files of 4 MB or more spool to disk. Prefer vdo_file_send_path and vdo_file_save for anything large.
  • Limits: 64 MB per file by default (file_max_bytes). The server keeps the 12 most recent completed incoming files.

Shared state

A small key/value store every peer in the room keeps a copy of. Each write carries a clock (a counter that only goes up) and an actor (the writer's stream ID). When two copies disagree:

  1. The higher clock wins.
  2. On a tie, the alphabetically later actor wins.

Every peer applies the same rule, so they all end up with the same value without a server deciding. Good for task status, assignments, and small flags. Not a database: keep values small. A session holds up to 2,048 keys by default, and vdo_state_set refuses new keys past that.

{ "name": "vdo_state_set",
  "arguments": { "session_id": "vdo_9a0e…", "key": "task.status", "value": "approved" } }

Networking

  • Direct first. WebRTC tries a direct path, which is fastest on a LAN and often works across the internet through NAT.
  • TURN fallback. If direct fails, traffic relays through VDO.Ninja TURN servers. Still end-to-end encrypted; a little more latency.
  • Privacy mode. force_turn: true always relays, so peers never see your IP. Some networks connect less reliably this way.
  • Hard blocks. Some corporate firewalls and WSL network setups block WebRTC's UDP traffic. TURN helps but isn't a guaranteed bypass.
  • No WebRTC at all? Use the HTTP relay: plain HTTPS POST and long polling through a server you run.
  • Not a tunnel. Only tool payloads cross the channel. No TCP, SSH, or port forwarding.
  • Reconnects. Heartbeats every 15 s. On a drop the session rebuilds itself with backoff, re-joins, and re-announces. Make your message handlers safe to run twice.

HTTP relay

For machines that can't run the native WebRTC library, or networks that block it. Both agents join the same encrypted room through a relay you operate. Messages, files, and shared state use the same tools.

WebRTC stays the default. Both participants must choose transport: "http" with the same relay settings; sessions on different transports don't see each other. There's no automatic switching yet.

1. Run the relay

Node 18+, no native dependencies. Generate two secrets: an access token for the relay and a separate room key for the clients.

# run twice: once for the token, once for the room key
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
VDON_RELAY_TOKEN=<token> npx vdon-mcp-relay
# listens on 127.0.0.1:8790 (VDON_RELAY_HOST / VDON_RELAY_PORT to change)

For other computers, put it behind an HTTPS reverse proxy: forward /v1/rooms/ unchanged, keep the Authorization header, disable caching, allow 768 KiB request bodies and 30-second responses. Remote clients must use HTTPS; plain HTTP is only accepted on loopback.

2. Point each MCP server at it

Machines that only use the relay can install without WebRTC: npm install @vdoninja/mcp --omit=optional.

{
  "command": "node",
  "args": ["/absolute/path/node_modules/@vdoninja/mcp/scripts/vdo-mcp-server.js"],
  "env": {
    "VDON_MCP_RELAY_URL": "https://relay.example.com",
    "VDON_MCP_RELAY_TOKEN": "<relay access token>",
    "VDON_MCP_RELAY_KEY": "<64 hex characters>"
  }
}

The relay only ever gets the access token. Keep the room key on the clients. vdo_connect also takes relay_url, relay_token, and relay_key, but environment variables keep secrets out of the agent's context.

3. Join and send

{ "name": "vdo_connect", "arguments": { "transport": "http", "room": "project_room", "stream_id": "planner" } }
{ "name": "vdo_connect", "arguments": { "transport": "http", "room": "project_room", "stream_id": "reviewer" } }
{ "name": "vdo_send", "arguments": { "session_id": "<planner-session>", "target": "reviewer", "data": { "text": "Please review the plan." } } }

What the results mean

You seeIt means
delivery_stage: "queued"Your local transport accepted the message. Keep the message_id to track it.
relay_receipt · relay_acceptedThe relay has it. Not proof the other agent read it; ask for a reply.
relay_receipt · delivery_unknownRetries failed; the relay may or may not have it. Check before repeating anything consequential.
relay_connectionThe reader lost or regained the relay. vdo_status shows the current state.
relay_history_lostYour cursor fell out of the replay window. Reconcile tasks, re-sync state, check unfinished transfers.
relay_message_rejectedAn event failed decryption or validation. Check room keys match and clocks are in sync.

Limits and privacy

  • Encryption: AES-256-GCM, key derived from the shared room key. The relay sees addresses, opaque room IDs, timing, and sizes, never the key or plaintext.
  • Shared key, shared access: anyone with the room key can read all of that room's traffic and claim any identity in it. A target picks delivery; it isn't a private channel. Use separate rooms for separate trust groups.
  • No forward secrecy: a leaked key decrypts previously captured traffic. Rotate keys when membership changes. Prefer WebRTC when that matters.
  • Replay, not storage: up to 512 events or 8 MiB per room for 5 minutes, 16 rooms per relay, memory only. Long polls return within 25 seconds.

Troubleshooting

My agent doesn't see any vdo_ tools

Restart the client after installing. Check the registration with claude mcp get vdo-ninja-mcp or codex mcp get vdo-ninja-mcp. For JSON-configured clients, make sure the script path is absolute and exists. If you moved the install folder, run npx vdon-mcp-install again.

The installer says a CLI wasn't found

It only registers with CLIs on your PATH. Install the missing one, use --codex-only or --claude-only, or configure the client by hand.

Both agents connected, but nothing arrives

Check both used the same room and password. Have one side set target_stream_id to the other's stream_id. Call vdo_receive with wait_ms: 1000 and look for data_channel_open. A send_rejected event with no_open_data_channel means the channel isn't up yet: wait and retry.

connection_failed, or it never connects

The network is probably blocking direct WebRTC. Try force_turn: true. Run MCP_DEMO_FAKE=0 npx vdon-mcp-demo-message on the same machine to separate network problems from agent problems.

sync_peer_rejected or protocol_auth_failed

A security check failed. Common causes: different join token secrets, an expired token, a stream ID missing from the allowlist, or one side requiring session MAC while the other can't provide it. vdo_sync_peers shows the reason per peer.

One agent is on the relay and the other isn't

Sessions on different transports never discover each other. Disconnect both and reconnect with the same transport, room, relay URL, token, and room key.

relay_history_lost or relay_message_rejected

History lost: you were away longer than the relay's replay window. Check unfinished work with your peers, run vdo_state_sync, and look at vdo_file_transfers. Rejected: room keys differ, or a clock is far off. Sync clocks and compare keys.

validation_error on a tool call

An argument is missing or misspelled (unknown keys are rejected), or the tool isn't in the active profile. vdo_capabilities lists what's enabled.
